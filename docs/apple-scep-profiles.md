# SCEP certificate profiles

The SCEP editor configures an external certificate authority for native Apple
certificate requests. It creates a versioned, encrypted profile; it does not contact
the CA when the operator saves or assigns that profile. Devices contact the CA
after receiving the configuration. This template is separate from OpenUEM's own
SCEP service for issuing MDM enrollment identities.

## Settings and compatibility

System scope supports iOS/iPadOS 4 and macOS 10.7 or later. User scope requires a
managed Mac user channel. The editor accepts an HTTP or HTTPS SCEP URL, an optional
CA instance name and challenge, subject attributes, alternative names, key options,
CA fingerprint and pending-response retry settings. URLs cannot contain embedded
credentials or fragments. HTTP requires an approved CA fingerprint; HTTPS can use
its TLS trust path without a separate fingerprint.

Subjects are encoded as nested X.500 relative-name arrays. The editor takes one
attribute=value pair per line, using the documented aliases or numeric OIDs, and
preserves the value after the equals sign. Uploaded profiles can also contain
multiple attributes within one relative name. Alternative-name values may be a
single string or an array for email, DNS, URI and NT principal names. The editor
preserves name case and writes arrays when more than one value is supplied.
OpenUEM does not substitute subject values; device-supported variables follow
Apple's behavior and the target device context.

The editor explicitly selects RSA with 2048 bits by default; 4096 and legacy 1024
are also available. Optional uploaded key settings remain optional. Key usage
supports unspecified, signing, encryption, or both. Some CAs accept only one use.
A CA fingerprint is binary SHA-1 or legacy MD5 data; the editor accepts hexadecimal
text with spaces or colons and validates its length.

Mac-specific minimums apply even when an option is explicitly zero or false:

| Option | Minimum macOS version |
| --- | --- |
| Retry count, retry delay and application access | 10.10 |
| Key usage | 10.11 |
| Private key export | 10.13.4 |

These options are also available on iOS/iPadOS from the payload's base version.
Leaving an optional setting unchanged omits the key. Retry count is bounded to
0–100 and delay to 0–86400 seconds. Subject/name lists have explicit size and count
limits. The parser rejects real numbers and strings where integer settings are
required, malformed subject structures, unsupported names, and nonboolean switches.

## Delivery and protected configuration

The challenge is encrypted with the catalog and retained revisions. Authorized
profile managers can download it as part of the profile; catalog pages and audit
records omit it. The CA controls the challenge's lifetime, permitted reuse,
subject authorization and issuance policy. Configure these for the intended
users/devices before assigning the profile.

Creation requires profile-management permission, CSRF protection and review
confirmation. The form rejects repeated, unrelated and query fields. Assignment
checks platform, channel and version. Catalog updates and restoration recheck
active System/User assignments and roll back snapshots, commands and catalog
changes together when a target is incompatible. Removal uses fresh native profile
inventory verification. Compatible Mac/iPhone batches remain supported.

Saving, assigning and reporting the profile installed do not prove CA issuance,
certificate renewal or successful application authentication. No server-side
certificate request, discovery or trust probe is hidden inside these operations.
Private keys are generated by the target's SCEP workflow.

## Validation and remaining acceptance

The isolated core check uses unchanged production code and shared helpers. It
passes SCEP parsing/building, plist round-tripping, omitted defaults, zero/false
settings, fingerprint data, HTTP pinning, subject/name structure, integer types,
platform/channel/version boundaries and the existing public-certificate checks.
Template formatting and generation pass.

Native tests cover System/User revision rollback, supported mixed-platform
assignment, encrypted challenge storage, audit privacy and verified removal. A
synthetic TLS issuer records zero requests during server-side profile operations.
Console tests cover roles, strict forms, unpinned HTTP, secret-safe errors, stored
minimal/User/HTTP variants and escaped display names. Every job in the
[`e3a559c` PR workflow](https://github.com/the-luap/openuem-console/actions/runs/34355132962)
passes, including native Apple race tests (490.663 s), handlers (13.122 s) and
desktop lifecycles (27.584 s). The [matching push workflow](https://github.com/the-luap/openuem-console/actions/runs/34355127393)
also passes every job.

Eighteen browser cases use the actual CI-rendered page: System/User scope,
minimal/advanced HTTPS and pinned HTTP at 390/768/1440 pixels. Defaults, required
URL and review controls, zero/false settings, multiline values, password control,
scoped submission and CSRF pass. Keyboard confirmation and submission work without
horizontal overflow; the narrow layout was inspected. Native selects are set
directly, so operating-system dropdown arrow-key behavior is not independently
verified.

Physical acceptance must use the intended CA and target OS versions to verify
issuance, key access/export behavior, trust, renewal and dependent application
configuration. [PKCS12 imports](apple-pkcs12-profiles.md) and ACME templates are tracked separately.
